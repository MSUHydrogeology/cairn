# Security code review -- Claude Opus 5.5 -- 2026-11-22: the Windows installer containment fix

Reviewed commit: a3435faaba55b833f35a2fb945ff5b37fcb18f73 ("Installer: on Windows the skill copy fallback refuses a link or junction before it writes"; files `install/_scaffold/install.py`, `tests/test_engine_copy_fallback_contained.py`, `CHANGELOG.md`)

**Obligation**: the Security Review of a write-containment change in the installer (a trust boundary: project contents decide where the installer writes and deletes)
**Tier**: Internal Security Review
**Findings**: raised (1 blocking, 5 non-blocking)
**Verdict**: REVISE

**Conclusion.** I found no way for the contents of a cloned project alone, with no other program running, to make the installer create, overwrite, rename or delete anything outside the install folder, or write bytes through a link, on Windows or on Mac and Linux. The POSIX path (Mac and Linux) behaves as before. Every remaining way out needs a second program running on the machine at the same moment (a "racer"), which `install/SAFETY.md` accepts ("no concurrent filesystem attacker"). One thing fails the bar: two of the delete safeguards the commit message names have no test that fails without them (B1). The fix is two test cases; no code change.

**Reach of the attack, as measured from the code.** Before this commit, `_assert_safe_write` (`install/_scaffold/security.py` 130 to 180) already refused a symbolic link at a copy or quarantine name and any name whose folder resolves outside the project. What it missed on Windows was a junction inside the project, a dangling junction at a quarantine name, and anything that appears after the check. A cloned repository cannot carry a junction, and Git creates symbolic links on Windows only where they are allowed, in which case the installer's probe (`_symlinks_available`) normally finds links work and links the skills instead of copying them; I did not check every caller that passes `allow_symlinks=False`. So on Windows the new checks mainly close racer windows and links made by other tools (an unpacked archive, say). That is worth having; it is not a repository-only attack being closed.

**Blocking**

B1. **Two delete safeguards that the commit message claims are not caught by any test** (`install/_scaffold/install.py` 875; test `tests/test_engine_copy_fallback_contained.py` 940). `_remove_created` deletes a file that may sit outside the project, so its guards are the part that must not drift. The message says "a file number of 0 is never trusted" and "not a link". Mutations, in a scratch copy of the tree outside the repo, running the whole test file there: (a) `created.st_ino and` removed: 59 passed; (b) `not _is_redirect(now) and` removed: 59 passed. Failure scenario for (a): on a filesystem that reports file number 0 for every file, the identity check shrinks to "same volume", so if the stray file is replaced before the delete (a racer), the user's file at that name on the same volume is deleted. (b) is mostly redundant today, because `os.lstat` of a link reports the link's own file number, which differs from the created file's; it is still a claimed control. Smallest fix: two cases in `test_only_the_file_this_run_created_is_removed`: pass a `created` record with `st_ino=0` that otherwise matches the real file and assert the file stays; and patch `os.lstat` (or use a fake record) so that the entry at the path matches the created identity but has `S_IFLNK` mode, and assert nothing is removed.

**Non-blocking**

N1. **The check after the open compares two path answers, never the open file itself** (`install/_scaffold/install.py` 1046 to 1049, `_created_elsewhere` 842 to 865). `created = os.fstat(...)` is taken but used only for the delete. A racer who plants a link at the temporary name, lets the open create the far-end file, then puts a plain file back at the temporary name before `realpath` runs, passes both path checks, and the skill bytes are written into the far-end file outside the project. The same works with a folder swapped for a junction and back. Racer-only, inside the accepted model. Smallest fix: before the write, also require `(created.st_dev, created.st_ino) == (os.lstat(tmp).st_dev, os.lstat(tmp).st_ino)` with a nonzero file number, as `_read_regular_bytes` in `dev/tools/session.py` already does for reads.

N2. **The delete by path can be redirected to a file the racer names** (`install/_scaffold/install.py` 874 to 877). Between the identity `lstat` and `os.unlink`, a racer who swaps a folder above the stray file for a junction makes the unlink remove a same-named file elsewhere (the name is the racer's choice, since it came from the planted link). The identity check cannot stop this; Windows has no `dir_fd` unlink, and the standard library has no delete through an open handle. The commit message discloses the gap ("that remove-by-path has its own tiny look-then-remove gap"). A same-user racer could delete that file directly, so this adds little power, but it is a delete primitive. Options for the Maintainer: keep it (current), or leave the empty stray file in place and say so in the refusal (no delete at all, at the cost of a zero-byte file outside the project).

N3. **A folder can be created outside the project under a race** (`install/_scaffold/install.py` 1026 then 1036). The folders are looked at, then `out.parent.mkdir(parents=True, exist_ok=True)` follows links. A junction swapped in between creates empty folders at the far end; `guard(tmp, out)` at 1038 then refuses, but the folders stay. The docstring's "looked at again just before ... a new folder" is true but leaves this instant. Racer-only. Smallest fix: say so in the docstring's best-effort sentence; creating each folder with a look before each `mkdir` would narrow it, not close it.

N4. **Only two reparse tags count as links** (`install/_scaffold/install.py` 807). Windows marks every tag the system treats as a name redirect with the name-surrogate bit `0x20000000`; besides the symbolic link and mount point, that set includes the silo global link (`0xA0000019`) and the container link (`0xA0000027`), which Windows follows inside containers. Cloud placeholders (OneDrive, `0x9000xxxx`) and app-execution links (`0x8000001B`) do not carry the bit, so they would still pass, which is right for question (f). The post-open check (N1 aside) is the backstop. Smallest fix: `st_reparse_tag & 0x20000000` in place of the two-value tuple, with the existing cloud-placeholder test kept and one test for `0xA0000019`. The same tuple is in `templates/skills/_lib/meter.py`, so a change there is a separate decision.

N5. **A refusal while copying (not while planning) leaves the run part-done** (`install/_scaffold/install.py` 1031 to 1055). The docstring's "a refusal leaves nothing half-done" holds for refusals in the plan phase. A refusal or a re-raised `PermissionError` at 1033 or 1054 comes after earlier copies are written, and at 1054 after this file's quarantine rename, so the copy name is empty and the user's diverged bytes are at `*.diverged.bak`. No user file is lost and the next run regenerates the copy. This was already true of any error in that loop before the commit. Smallest fix: none needed; optionally name it in the docstring.

**Questions asked, answered.**
- (a) Outside writes, renames, deletes: none from project contents alone; racer windows N1, N2, N3 remain, all accepted by `install/SAFETY.md` 235 to 251.
- (b) Bytes through a link: not without a racer (N1 is the racer case).
- (c) Attacker-chosen delete: the identity check (same volume and file number, not a link) correctly refuses a file replaced before the check and a link at the path, because `os.lstat` does not follow the last name. A file replaced after the check, or a folder swapped above it, is N2. The two guards lack tests: B1.
- (d) Leaks: none new. Every refusal prints the project-relative name through `shown` and `ascii` escaping (950 to 955); `guard(tmp, out)` shows the copy name, not the random temporary name; the far-end path (`stray`) is never printed. A re-raised `PermissionError` carries its own path, as before.
- (e) Crash or wrong blame: `_link_in_path` turns any `lstat` error into "found" (a refusal), never a crash. A `PermissionError` at a rename becomes the link refusal only when a link or junction is actually at or above that name; a sharing violation with no link stays the original error (test `test_a_denied_rename_is_not_called_a_link_when_no_link_is_there`). A folder that cannot be read is reported as a link: wrong words, safe direction.
- (f) Reparse tags: the two tags are read correctly, and a cloud placeholder passes (test id `another-reparse-point-is-not-a-link`, tag `0x9000001A`). See N4 for the tags left out.
- (g) POSIX: unchanged. On Mac and Linux `_ON_WINDOWS` is false, so `guard` does nothing, `check` is as before, `created` and `stray` stay `None`, `_remove_created` is never called, and the two new `except PermissionError` blocks only re-raise.

**Claims checked as acceptance tests.** Each claim in the commit message, and whether a test fails without it:
- Plan-phase look at every name: yes (the commit's 13 mutations; I did not repeat them).
- Look again before a rename or new folder: yes, except the copy-rename look on the Mac, as disclosed.

**`_write_replacing` in `dev/tools/session.py` (and `templates/skills/_lib/session.py`).** A separate finding, not reviewed here. It opens a random temporary name without `O_NOFOLLOW` on Windows and has no post-open check. Its callers' `_assert_not_linked` (687) refuses a symbolic link at the name or a folder above, and a junction whose folder resolves outside the project; a junction inside the project passes. The 16-hex-digit random name cannot be planted from a repository, so I see no route from project contents alone; it is reachable on Windows only by a racer, the same accepted window. It should get its own issue on the board, with N1's identity check as the likely fix.
