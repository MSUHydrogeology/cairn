## Foundations

1. **Does it really do what it claims?** Mostly yes, with one hole. The reading order, extraction from raw objects, byte comparison, isolation, anchor-sourced encoder, key checks, one prompt and the fail-closed re-run check all behave as written and 100-odd breaks of them were caught. The hole: the `repin` process imports from a folder a commit controls, and a committed package marker or module named `bootstrap` or `scripts` runs before the compare reaches it. -- `scripts/repin.py:235-250`; probe in the ledger (L1).
2. **A simpler or safer build?** Load the ten listed modules by file location under their dotted names, with empty parents made in memory, and never put the extraction on `sys.path`. That removes the whole class behind B1 (and any later optional-import shadow) instead of listing names. Also: judge a loaded module by `__spec__`, not by its own `__file__`, which a module can reset. -- `scripts/repin.py:236-250`.
3. **What input or run breaks it?** Commit bootstrap/__init__.py (or scripts/__init__.py, or a root `scripts.py`) holding a marker write and `__file__ = None`; `repin status` ran it, printed "10 files equal the anchor's entries" and exited 0. Also: `--first-run` with only a lockfile correction owed refuses and names a runbook with no lockfile step. -- ledger L1 and L2; `/private/tmp/claude-501/-Users-kendal30-Code-cairn/66d87e18-52ca-44fc-b226-0817c96bdc10/scratchpad/probe_init.py`, `probe_fr.py`.

## Blocking findings

**B1. A committed `__init__.py` or same-named module runs in the `repin` process before any check on it, and can hide itself from the post-import check.** The pre-import compare covers the 10 listed files. `import bootstrap.tests...` and `import scripts.reanchor_ceremony` search the extraction root, where `bootstrap` and `scripts` are plain folders (namespace packages). A tracked bootstrap/__init__.py (matches the frozen glob `bootstrap/*.py`, so a `FROZEN-NEW` row, which the rules allow), scripts/__init__.py, or a root `bootstrap.py` / `scripts.py` takes precedence and runs. With `__file__ = None` in the payload, the check at `scripts/repin.py:241-243` skips it (`if not f ...: continue`); without it the module is refused, but only after it ran, so "Nothing further ran" is false. This is the plan's SB1 "attack from the tree alone", and its tests only plant standard-library names. *Fix:* (a) minimal: before any import, refuse a tracked bootstrap/__init__.py, scripts/__init__.py, or any root entry whose stem is `bootstrap` or `scripts`; (b) better, per Foundations 2. In both, judge a loaded module by `__spec__.origin`, not its own `__file__`. *Tests:* a committed marker file for each of the four shapes, with `status`, `package` and `ceremony` leaving no marker (control: the anchored tree passes). This edits `scripts/repin.py` and its tests, so the next-certifying-run and the `--reviewed-commit` id move (plan M2).

**B2. R5 blocks the plan's M2 on the real tree, and its trigger measured a different thing.** `check_first_run` refuses when `build_transaction` returns anything, and R5 made the lockfile a transaction output (`scripts/repin.py:860`, `:532-534`). On HEAD, `repin package` shows one lockfile correction (drops the dev/collaboration_agreement.md record; file removed in `2cc6b260`). I measured in a scratch bed that a lockfile-only correction makes `--first-run` refuse with "Pin it by hand under bootstrap/AST_BASELINE_RUNBOOK.md first", and that runbook has no lockfile step (`grep -i lockfile bootstrap/AST_BASELINE_RUNBOOK.md`: nothing relevant). So after M2's hand AST pin the first run still stops, with advice that cannot be followed. The R5 trigger (`verify_integrity.py` exits 1) fires on 23 edited-file mismatches (I reproduced: rc 1, 23) that the correction never touches; after R5, that command still exits 1. The implementer disclosed this; the right move under the stopping rule was to ask. *Fix (planning session or Maintainer picks):* either `--first-run` ignores a lockfile-only correction (it carries the same unpinned-bytes worry only for the AST pin), or M2 and the runbook gain "drop the stale record by hand". Also restate R5's trigger as "`status` says a lockfile correction is owed". Test: first-run with only a lockfile correction owed (the two cases above, each with a control).

## Non-blocking findings (each with a recommended fix)

**N1. The isolation test cannot see a missing bytecode folder.** `test_the_repin_process_runs_isolated` matches `compiled files go to (\S+)`, and "None" matches. With the prefix line removed it still passes (mutant PYC). The prefix is belt-and-braces for the extraction (tracked `.pyc` is refused), so this is a weak oracle, not an open hole. Fix: assert the value is a real folder under the temp dir.

**N2. The SR-3 test cannot fail on the thing it names.** Replace the apply step's render with the stored `summary` text, or delete it: the test still passes, because `package` already prints the same rows into the same screen (mutants SR3 and SR3b). Behaviour in the CLI path is right (`scripts/repin.py:648-651` renders from disk against `new_text`). Fix: a test that hands `apply_pin` a transaction whose stored `summary` lies, and asserts the real changes are on screen.

**N3. The end-of-ceremony verification has no end-to-end test.** `test_checkpoint_verification_...` tests `verify_checkpoint` alone. Deleting the `if not good: raise` (line ~1013), or verifying the old anchor instead of the new one, passes every test (VER, DONE, VERb). The code is right. Fix: one run with `verify_checkpoint` patched to fail, asserting no "Done"; add `new != anchor` before "Done" (an unmoved anchor would currently print "the new anchor is" the old one; I did not measure whether the launcher can exit 0 that way).

**N4. Five criteria the plan names have no test that fails.** (a) Stage 1's short environment (`scripts/repin.py:969`; `env=dict(os.environ)` survives); (b) children's `PATH=/usr/bin:/bin` (CHILD_PATH from the caller's PATH survives); (c) `rc.check_packet_pair` call (dropped, all 61 ceremony tests pass); (d) launcher `hash-package` agreeing with the script's own hash; (e) the private copy of `reanchor.sh` re-hashed before each call. Fix: one test each, or a one-line note in the plan that the launcher's own checks are the cover.

**N5. The post-write byte check, the second compare-and-swap, and two preimage hashes are unpinned.** Dropping the independent on-disk hash after the write (`here = dict(blobs)`), the compare right before each replace, or the `new_sha256` and `preimage_sha256` comparisons passes the tests. The first two are time-window checks; the rest are bookkeeping beside the raw-file equality that is tested. Fix: a test that has `os.replace` write other bytes (the existing "sneaky" harness shape).

**N6. Extraction refusals the plan lists are unpinned, though they work.** Tracked symlink and submodule refusal, the outside-folder check, the `..` refusal and the read-back compare all survive removal. I measured by hand that a tracked symlink and a gitlink are refused, and that `..` and `.git`-named paths are refused. The `..` and outside-folder checks are a redundant pair (each alone survives); with both removed, a file named `..` fails only on the filesystem, and I did not conclude whether a nested `..` tree then escapes (my probe was inconclusive). Fix: one refusal test per kind.

**N7. The launcher is hashed once, then run twice from the ceremony folder with no re-hash** (`scripts/repin.py:891`, `:970`, `:998`), minutes and two prompts apart. The artifact gets a private copy and a re-hash before each call; the package is re-hashed after Summary 2. A same-user process is inside the accepted limit, so this is a gap in symmetry, not a new exposure. Fix: measure whether the launcher can run from a private copy as the artifact does; if not, re-hash before each run and say so in the record.

**N8.
