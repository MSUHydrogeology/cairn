## Findings

None blocking. Each is the reviewer's recommendation; the author decides.

**F1 -- The encoding of status text is correct but nothing pins it. (Should fix; test only.)** Mutant M3 (the board advisory printed through `str` instead of the encoder) and M24 (the shared builder prints `status.split()[0]` unencoded) both survive all 1262 tests. A command-line probe under each shows U+0000, U+0007, U+001B, U+034F, U+202E, U+2066, U+2069 and U+E0041 in the output, in the board for M3 and in both tools for M24. Dropping the encoding of the artifact *name* is caught (M25, by `test_skills_security.py::test_hostile_artifact_name_cannot_forge_orientation_lines`), so the status is the gap. *Fix:* add one test per tool through the real entry point (`board.main` and `session-start`) with an ESC, a NUL, a bidirectional override and a 10,000-character status, asserting no control or format characters and a bounded line. It belongs in `test_status_vocabulary_advisory.py`, not a frozen file.

**F2 -- The board and session-start disagree on bold or italic statuses. (Fix.)** `**Status**: **awaiting-decision**` and `*awaiting-decision*`: the board flags them "unknown", session-start passes them. Cause: session-start's `_status_of` strips `*` from the value (`tools/session.py:984`); the board hands over its raw header value (`_header_fields`, `tools/board.py:151`). `_status_problem` does not normalize. *Fix:* strip leading and trailing `*` inside `_status_problem` (idempotent for the session caller) so both tools judge one file the same way, and add an agreement test. Underscore italics are flagged by both, which is consistent.

**F3 -- The retired set omits two of the six retired tokens, and its comment names the wrong source. (Fix.)** `_RETIRED_STATUSES` (`tools/session.py:1004`) lists four; commit `3defdb78` retired six: `proposed`, `reviewed`, `revised` and the plan tokens `open`, `executing`, `review`. `open` and `review` therefore read "unknown" instead of "retired". The comment above it says all four are the words "refused on an active one", but that sentence names three. Both labels still flag the artifact, so this is a label, not a miss. *Fix:* add `open` and `review`; point the comment at `doctrine/lifecycle.md:152-155` for three and at `3defdb78` for the plan tokens; add a test node. `doctrine/plans.md:158-159` still draws `open --> ... executing --> review` as live states; it is rule text, so I only note it for the Maintainer alongside the lifecycle sentence.

**F4 -- Four guards survive every test. (Fix with tests.)** All behave differently under the mutation, measured through the real entry points: M12 (drop the blank-status guard) makes the board print a traceback at `_status_advisory` on a blank `**Status**:`, which is exactly the crash that would abort session-start before the binding resolves (ruling 1); M11 (drop the placeholder guard) makes session-start print `((no: unknown)` for an artifact with no Status line; M10 (print the whole status) shows `proposed -- old note` instead of `proposed`; M13 (drop the backtick allowance) flags `` `awaiting-review` ``. *Fix:* one test with a blank status and a no-status artifact in both tools (rc 0, no advisory, no traceback), one with a flagged status followed by a note, one with a backticked allowed word.

**F5 -- Three different "word then note" rules now exist, and the new one is loose at the edges. (Low.)** The new regex (`tools/session.py:1009`) takes `[A-Za-z0-9_-]*` as the word, so `awaiting-decision--note` and `awaiting-decision-` are flagged while `awaiting-decisioné` and `awaiting-decision` plus a zero-width space pass (the word ends at the first other character, so an invisible or accented tail is ignored). The board's own Maintainer-list rule (`tools/board.py:63`, a lookahead that excludes letters, digits and underscore but not the hyphen) disagrees: for `**Status**: awaiting-decision-x` I ran the branch's board and `--maintainer` lists it as waiting on the Maintainer while the plain board calls its status "unknown". The reader recipe in `docs/build-a-board-view.md` uses a third rule (`^[a-z-]+`). *Fix:* accept the word only when it ends at end of text, whitespace, or ASCII punctuation (so a non-ASCII tail is flagged), and decide the hyphen case once for both rules; I would flag `awaiting-decision-x` in both.

**F6 -- A second walk over the same files. (Low.)** `_in_flight_status_advisory` (`tools/session.py:1043`) repeats the directory walk, the `_template.md` exclusion and the file read that `_in_flight` (`:1057`) just did. The exclusion lists can drift (the board already skips every `_`-prefixed file; session-start only `_template.md`, which predates this change). *Fix:* have one helper yield `(kind, name, status)` and build both the list and the advisory from it.

**F7 -- The advisory line has no cap. (Low.)** With 500 active artifacts (200-character names, 10,000-character statuses) the session-start output grows from 237,018 to 466,156 bytes, and 229,278 of the added bytes are one line. The in-flight list already grows the same way, so this doubles an existing cost rather than adding a new one, and the interpreter section still ends the run. *Fix:* name the first ten and end with "and N more".

**F8 -- Nothing ties the vocabulary table to the doctrine. (Low.)** `_STATUS_VOCABULARY` is pinned only against a hand-typed copy in the new test. If the doctrine gains a status, every artifact carrying it is flagged until someone notices. An existing helper, `_lifecycle_diagram_holders()` in `test_board_json_contract.py` (used at `:1399`), already reads the status words out of `doctrine/lifecycle.md`. *Fix:* one test comparing the table with it (and with the plan states in `doctrine/plans.md`).

**F9 -- The commit leaves two more lockfile hashes stale. (Process; the planning session decides.)** `dev/.cairn/cairn-lock.yml` records `tools/board.py` as `203c5919...` and `tools/session.py` as `17ac9b63...` (verbatim installs); the edited files hash to `86b890f1...` and `33c6b81b...`. `python bootstrap/verify_integrity.py --target .` lists 22 hash mismatches on the parent and 24 on `a773e753`, the two new ones being exactly these files. The repo already carries 22, and the open repin work is the queued remedy, so I do not call it a defect of this commit; it should be counted in whatever finalizes the lockfile.

**F10 -- The authority line cites a paragraph that excludes this change. (Process; no code change.)** The commit's `Defect fix:` line rests on "Fixing an easy problem you meet", which says the fix "adds no file, function, option or public name". This change adds a test file, three functions and three constants, edits `docs/tool-usage.md` and the board's own docstring (which promised "no judgment about whether a status is legal"), and edits `CHANGELOG.md` (a shared communication file the rules edit only at defined points).
