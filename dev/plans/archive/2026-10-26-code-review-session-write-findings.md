## Rulings on the five points

1. **The new loop in `_binding_untrusted`: sound; no earlier outcome changes.** I ran the parent's and the fix's `_binding_untrusted` on the same 17 stubbed index listings in one scratch project (empty; exact binding; ASCII-case and long-s spellings; gitlinks `dev`, `DEV`, `de`, `dev/.cairn`; unrelated files; an interpreter tracked or held by a gitlink; both orders of interpreter and binding; a malformed record before and after an interpreter match; git exiting 128). The two give the same answer on 12 of the 17. The other 5 differ only as intended: a fold match now carries the added text "git tracks it as ..." (3 rows), and when an interpreter is passed the two interpreter rows return the new reason. The early-return question: the parent has no interpreter reason, so nothing it returned changes. A malformed record after an interpreter match gives "unverified" in both, and a later exact binding match still wins ("tracked"). Mutant M31 (return at the first interpreter hit) survives, and it can only change which warning text prints, since every one of these ends in `fallback-untrusted`.
   *Identity checks.* Hard links at other depths are rightly not checked: I measured in git 2.53.0 that a checkout writes the new bytes to a new file and leaves a hard link on the old bytes (file `x` read B, its link `h` read A, two inodes), so a hard link cannot carry a checkout's bytes into the binding. Probe: a tracked hard link of the binding at 1, 2 and 4 path parts is trusted, as designed. A tracked symlink beside the binding is trusted too (its `lstat` is its own identity; correct). `st_ino == 0` is a real false positive that fails closed (F2). *The `160000` branches:* the 1-part branch (a gitlink the disk says is `dev`) is tested only with a patched `os.lstat`; that is as far as a test can go here, because no folder alias exists on APFS. It is enough to pin the mechanism (M09 is killed). The 2-part branch (`dev/.cairn`) has no test at all (M10, M11 survive, F4). *Cost:* with 30,000 three-part index entries `_binding_untrusted` takes 0.023 s on the parent and 0.20 s on the fix.
2. **SW-SR-11: right for a symlinked root and for the submodule reason; wrong on a case-insensitive disk (F1).**
   *Symlinked root:* measured. With the project reached through a link and the interpreter spelled with the real path, the kernel falls back after the checkout. A binding that names a link spelling never reaches this code, because `_has_symlink_component` refuses it first (`tools/session.py:669`). No test covers it, though (M04 survives).
   *Case-insensitive volume:* measured at resolver level with real git. `Path(interpreter).relative_to(root.resolve())` is case-sensitive. With the project in `CaseProj2` and a binding naming `.../caseproj2/env/bin/python3` (the same file on this disk), before the checkout the result is `local-env.json`, and after a checkout that makes git track the program it is still `local-env.json`. The control with the exact spelling gives `fallback-untrusted`. Why a mismatch is plausible: on this Mac `os.getcwd()` and `Path.resolve()` keep the case as typed (`/users/kendal30/code/cairn`) while `git rev-parse --show-toplevel` returns the on-disk case (`/Users/kendal30/Code/cairn`), and the installer writes `Path(sys.executable).resolve()` (`bootstrap/_scaffold/install.py:438`). I measured each link of that chain separately; I did not run the installer end to end.
   *`_INTERPRETER_TRACKED` for an interpreter held by a submodule:* right. The finding asks for one reason under "the same fold and the same `160000` prefix rule", and the remedy (name an interpreter git does not track) is the same. "Tracked by git" is loose for a submodule's files; it does not mislead.
3. **SW-SR-15 and `proc.stderr`: both a gap and out of scope.** The finding lists seven sites and does not list child output, so the fix is complete against the finding. The same class remains in `tools/session.py`: three `_warn(... proc.stderr.strip())` calls (`:1754`, `:1788`, `:1823`) and `sys.stdout.write(proc.stdout)` print the child's text raw. The children do not use the encoder (zero hits in `tools/intent.py`, `tools/evolution_infer.py`, `tools/prune_intents.py`), and `tools/prune_intents.py:75-78` prints the log path raw and uses `repr()` on fields, which leaves U+3164 raw. The kernel shows child stderr only when the child exits nonzero. This is by reading; I ran no child. A reader should treat any "reported:" line as unencoded child text until F5 lands. I recommend logging it as a follow-up finding, not holding this answer for it.
4. **The stat-failure fallback: consistent with the module; no Security Review owed in my reading; the planning session decides.** `tools/session.py:820-825` returns `_BINDING_UNVERIFIED` when `os.stat(cfg)` or `os.lstat` of `dev` or `dev/.cairn` raises `OSError`. That sends one more cause into the existing fallback ("An unanswered question is not an answer of no", the docstring says) and cannot grant trust. It adds no new disposition: fall back with a warning is the disposition already there, and the alternative (let the error escape) is the traceback class SW-SR-14 just closed. The finding names no behaviour for a failed `stat` of the binding, so this is a choice beyond its text, and AGENTS.md reserves "fallback disposition" changes for a Security Review; my reading is that this does not change the disposition. An honest run cannot newly hit it: reading the binding already needs search permission on exactly those folders (reasoned, not measured with `chmod`). Measured: each of the three stat errors returns `_BINDING_UNVERIFIED` even when git says nothing is tracked. Two cheap gaps: no test pins the direction (M15, which makes a stat failure mean "trust", survives), and the warning text says "could not ask git" for a cause that is not git (F6).
5. **SW-SR-10 wording: honest about the gap, incomplete about its reach (F3).** The docstring sentence (`tools/session.py:935-941`) and the SAFETY.md paragraph (`bootstrap/SAFETY.md:260`) both say the gate proves only that git's index does not list the file now. They name the four routes the finding names (archive then `git init`, `git apply`, `git reset`, `git rm --cached`) and say the full fix is separate and later. What they leave out is in F3: the program also runs under `session-end`, "arguments the kernel fixes" reads as a limit it is not, and the most common route for a research group (copying the whole working folder) is not named. The docstring points at `bootstrap/SAFETY.md`, which exists only in Cairn's own tree; the module already points at `bootstrap/tests/test_session_kernel.py` the same way (`tools/session.py:120`).

## Findings of my own

Each is a recommendation; the author decides. None blocks.

**F1 -- The in-project interpreter check is case-sensitive on a case-insensitive disk. (Should fix; about three lines and one test.)** See ruling 2 for the measurement. The cause is `Path(interpreter).relative_to(root.resolve())` at `tools/session.py:829-830`; the finding's recipe says exactly that, so the fixer followed it. *Fix:* compare folded strings instead: `folded_interp = _canonical_caseless(Path(interpreter).as_posix())`, `folded_root = _canonical_caseless(root.resolve().as_posix())`, and take the project-relative part when `folded_interp` starts with `folded_root + "/"`. Over-folding only makes the gate stricter. *Test:* in the new file, the real-git checkout test with the binding's folder part upper- or lower-cased (skip when the disk is case-sensitive).

**F2 -- A disk that reports inode 0 makes every 3-part index entry look like the binding. (Low; fails closed.)** With `st_ino` forced to 0 for all files, an unrelated tracked `a/b/c.txt` returns the "tracked" reason and names that file (measured with a patched `os.stat`/`os.lstat`; the control with real inodes returns trusted). The effect is a wrong refusal and a wrong "git tracks it as ..." text, never a trust. *Fix:* in `_has_identity`, return `False` when the identity's inode is 0, and in the cfg identity too.

**F3 -- The SAFETY.md paragraph understates the accepted gap. (Should fix; prose, claim-check it.)** (a) It says the program is run by `session-start`. The same resolver also feeds `session-end` (`tools/session.py:1966` and the handoff steps at `:1978-2005`) and the agent and session naming in `_intent_whoami` (`:426`), so goodnight runs it too. (b) "With arguments the kernel fixes" reads as a limit. The binding needs only an executable file, so the arguments do not constrain the program: say that it can be any program, with the operator's own permissions. (c) A fifth route is not named: copying the whole working folder (a zip, a synced or shared drive, a lab-mate's copy). The binding is ignored by git, so it travels with the folder. It also needs the named program to exist at that absolute path on the new machine; I argued this from the code and did not run it. (d) The gate has never run on Windows or on an HFS+ volume (the binding tests skip on Windows, and SW-SR-12 says a run is owed); one sentence saying so keeps the CHANGELOG line "even when the disk equates two spellings of its name" from reading as a claim for every disk.

**F4 -- Eight breaks pass every test. (Should fix; small tests in the new, unfrozen file.)** Mutants M04, M05, M08, M10, M11, M14, M15, M16 in the ledger. Each of M04, M05, M08, M10, M11, M15 and M16 was shown not equivalent by running the real entry point under the mutation and getting a different answer (the probe column). **F5 -- Child output reaches the terminal raw.
