# Plan: Antigravity usage counts toward a project

**Source proposal**: dev/proposals/archive/2026-11-21-claude-usage-counting.md
**Status**: awaiting-code-review
**Plan review**: required(Internal + Internal Security Review)
**Opened**: 2026-11-22
**Rules that apply**: dev/rules/protected-surfaces.md, dev/rules/working-agreements.md, dev/rules/conventions.md, dev/rules/development-environment.md, dev/rules/custom_session_routines.md
**In brief**: The usage meter will count Antigravity's token use toward a project, once per reply and tied to a conversation and a time, so its usage can be reported per project like Claude's and Codex's.

## Build summary

After this plan the meter counts Antigravity token use once per reply (the tool writes each record about four times) toward the one listed project that the conversation's own saved files name. A conversation that names none, or several, counts toward no project, and the report says so and labels the project figure as inferred. Each reply carries a one-way conversation fingerprint and a time; a names-only check found that fingerprint does not match the run ids agents declare (0 of 10), so the later cost-per-plan work needs another join. Antigravity rows carry input and output only (no model, no cache counts), so the pulse shows weighted=unknown for them: they say how many tokens, not what they cost. Every project's report shows INCOMPLETE, once on its header line, while any Antigravity conversation is unattributed. Counting starts only when the Maintainer adds Antigravity to his consent file; no agent does. His words do not name attribution by saved files (option B); the plan builds it and asks him once to confirm (W2).

## Scope

**Result.** An Antigravity reply is counted once, with a conversation fingerprint and a time, toward the one listed project its conversation names, or toward none. "Listed" means named in the Maintainer's consent file.

**Measured by the look** (counts only, one Mac, one moment): 24,339 records hold both token fields and a text time, none a folder; 6,134 are distinct; 92 name a model; of 48 conversation folders, 40 name this project's root in their saved files and 5 name it and another folder. **Closed by a seventh count-only probe** (the Mac, 2026-11-22, at the Maintainer's word "do what's needed"; added to [the look's record](../measurement/antigravity-look-2026-11-22.md)): the time field is `created_at`, an ISO-8601 text with a time, in all 12,268 token records of `logs/`; none of those records names a model (`model`, `modelName` and `model_name` appear in 0 of 12,268; the look's 92 were in the `chunks/` copies, by subtraction), so every Antigravity reply's model is unknown; a token record names no conversation, so the run identity comes from the folder name; and each of the 6,134 keys appears exactly twice in `logs/`, so none appears four times and no collision was found. `created_at`, `conversationId` and `conversation_id` join the names list in `dev/rules/custom_session_routines.md` ("the keys the reader reads") in C3. **Checked by names only** (the Mac, 2026-11-22; the entry names in `brain/`, nothing inside a folder opened): none of the 10 distinct `antigravity-<8 hex>` run tags in `dev/intents.jsonl` equals the first 8 characters, or `sha256(name)[:8]` (how `_session_digest` in `dev/tools/_intent/identity.py` writes a tag), of any of the 47 UUID-spelled names (of 48 entries). So the folder name is not shown to be the id agents declare under; the check cannot tell a different id from folders missing on this Mac. Still unknown: which it is, and so whether `ANTIGRAVITY_TRAJECTORY_ID` equals the folder name.

**Rules.**
1. **Read set.** Only `*.jsonl` files directly inside `brain/<id>/.system_generated/logs/` under the consented root, `<id>` a canonical lowercase UUID; not `logs/chunks/`, which the look measured as repeats. A line is a reply only if it is a top-level JSON object with `input_tokens` and `output_tokens` as non-negative whole numbers (no booleans) and a zone-aware time in the named field. A line with neither token field is skipped, unless it holds a `usage` key at any depth, which gives `unsupported_usage_contract` (the stub's reason), so a format change shows. One field, a bad number or a bad time gives `invalid_record` and no event. The conversation id is the second part of the stream's `relative` path and must satisfy `str(uuid.UUID(x)) == x` (`_codex_uuid`, 3476); for synthetic lines `read_records` takes a keyword `conversation`, and C1's tests pass it. A complete token record with no usable id, or whose conversation is absent from `attribution` (rule 5's result, passed in), gives no event and `invalid_record`. A record whose `conversationId` or `conversation_id` names another id gives no event and `conflicting_binding` (the seventh probe found no record naming one; this guards a format change).
2. **Kinds.** Input is fresh input and output is output; both cache kinds are unknown (`None`, never 0), as Codex's absent cache-write is. I assume `input_tokens` may include cached text. The model is always unknown (`None`): no token record in `logs/` names one (0 of 12,268), so the reader has no model branch. `_weighted_reference_tokens` (3641) already gives no total when a kind or the model is unknown, so none is invented.
3. **Duplicates.** The key is a digest of tool, conversation, time, input and output; the existing merges join copies within a file, across files and across refreshes. One case goes wrong: two genuine replies alike in all four count once, an undercount. Accepted. Scope gives the seventh probe's count: each key twice in `logs/`, so no collision was found in this data.
4. **Run identity** (one agent's stretch of work; here a conversation). Thread and session are the conversation id, stored only as `_digest("antigravity", id)` and `_short_session_digest(id)`, the helpers Claude's reader uses. The time is the record's. No raw id or path is stored or printed. The names-only check under Scope found no match with the run ids agents declare, so this fingerprint cannot join a declared stage as built; the cost-per-plan plan owns what follows (another join, such as a time window inside a declared stage and project, weaker where runs overlap, or leaving Antigravity out).
5. **Attribution (the trust change).** A conversation is the folder `brain/<id>/`. Searched: regular files up to 8 levels down ending `.txt`, `.md`, `.json`, `.jsonl` or `.log`, links skipped, read in 64 KiB blocks. A file names a project when the project's path text from the consent file occurs in it, exact case, with the byte before not a letter, digit, `.`, `_`, `-`, `~`, `%` or `/` (the literal `file://` excepted) and the byte after not a letter, digit, `_` or `-`. So `/a/cairn-old` does not name `/a/cairn`; a `.` counts as an end when the byte after it is not a letter, digit, `_` or `-`; any byte of 0x80 or above after the root blocks a match; blocks overlap by the longest listed project path's length plus 8 bytes, so a match with the 7 bytes before it and the 2 after it falls whole in one block; on Windows the doubled-backslash form counts too. Exactly one listed project named: the replies carry it if that project passes `verify_project`, as Claude's do (defined 3893, used at 4047 to 4055; a failure leaves the replies unattributed with its reason); `current_local_verified` and `proven` here mean only that this rule held. None named: `antigravity_project_not_named`. Two or more, a listed project nested in another included: `antigravity_projects_ambiguous`. An unlisted folder named is ignored. Only which projects matched leaves the search. The three attribution reasons (`antigravity_project_not_named`, `antigravity_projects_ambiguous`, `antigravity_search_incomplete`) are event reasons, not batch issues.
   **Bounds** (my starting values, not measured): 16 MiB read, 5,000 entries and 8 levels per conversation; over, or an unreadable file, gives `antigravity_search_incomplete`, never a guess. A conversation is searched only if `attribution_bytes + MAX_ATTRIBUTION_BYTES <= MAX_ATTRIBUTION_RUN_BYTES` (256 MiB) and `total_bytes + MAX_ATTRIBUTION_BYTES <= MAX_RUN_READ_BYTES`; otherwise it waits for the next refresh (`catching_up`) and its files are skipped as at 2829 to 2834. Search entries and bytes charge only the per-conversation caps and a per-refresh cap of 50,000 entries (`MAX_ATTRIBUTION_RUN_ENTRIES`, shared with the log walker's listing); over it, conversations wait (`catching_up`); the log walker stops at 2,000 conversations (`MAX_ANTIGRAVITY_CONVERSATIONS`) the same way; nothing in Antigravity's reader raises `source_budget_exceeded`. Each opened file's `fstat` device and inode must equal the walk's `lstat`, or the search is incomplete. The search runs once per refresh for a conversation with new log bytes and stops at the second project named. An event keeps the project it was read under; seen later under another it becomes unknown (`conflicting_binding`, `_merge_retained_event`, 1814).
   **Weakness.** Text can name a folder for any reason. Anything that can write under `brain/<id>/` can move a conversation's tokens into a listed project, or out of all by naming two. The harm is a wrong number in a report; the attribution grants nothing and no gate reads it, though the claim-to-artifact join reads `proven` events too (`_build_mappings`, 3116 to 3120), so a wrong match can map a reply to a claim; the export tells inferred rows by tool and reason.
6. **Label and gaps.** Two coverage reasons, no new column or schema change. `_project_export` (2394) adds `antigravity_project_inferred` when its rows include tool `antigravity`; `_new_ledger` (3246) adds `antigravity_unattributed` when a project-less aggregate row has that tool. Unattributed tokens stay in the ledger's project-less rows (`_recompute_aggregates`, 1977), private; a project's export would misattribute them. Neither reason is on `_PULSE_BENIGN_REASONS`, so the pulse prints INCOMPLETE with them, once on the report's header line (`pulse.py` 880 to 886), with no `pulse.py` change. `antigravity_unattributed` rides the ledger's reasons, which every project's export copies (2394), so every project's report, Claude- and Codex-only ones too, shows INCOMPLETE while any Antigravity conversation is unattributed (the look found 4 of 48 that name no folder), and it no longer tells a cut-short refresh from this; accepted, since unattributed tokens may be any project's. A benign reason is not printed (`pulse.py` 466 to 469), so making one benign would hide the label, not fix it; no change is offered.
7. **Reach and consent.** The consent file already accepts `antigravity` (`TOOLS`, 38; `validate_config_bytes`, 301). The Maintainer adds the source, root `~/.gemini/antigravity` written absolutely, himself or by a clear yes in chat; no agent creates or edits `~/.cairn/meter.json`. The generic walker `_enumerate_jsonl` (406) would also read `logs/chunks/`, and its 100,000-entry limit (176) fails the refresh for every tool; the look's 9,330 files left out program folders, so the real entry count is unknown. New `_enumerate_antigravity` instead builds every path from fixed names (`brain`, a UUID folder, `.system_generated`, `logs`) and listed entries, never from record text or `..`, skips links at every level, refuses a linked root (the refresh is then unavailable, as for a missing root today) and opens the search's files with `O_NOFOLLOW` where the platform has it (Windows does not, 335; there the `fstat` and `lstat` check in rule 5's Bounds is the only tie to the walk, and no open checks a middle folder). Log reads keep the stream's open (827). It returns `(files, entries, waiting)`; the scan adds neither count to `total_entries` or `total_files` and sets `catching_up` when `waiting`, so a large `brain/` cannot raise `source_budget_exceeded` for Claude or Codex (2814 to 2817). A missing `brain/` or `logs/` gives no files; an error inside one conversation skips it with `catching_up`; only a missing or linked root raises `Unavailable`, which ends every tool's refresh (2813). A skipped conversation's cursors drop; its logs are read again from their start under the start filter, and the existing merge counts each reply once. It never lists the root's parent, so the credential file in `~/.gemini/` is unreachable even from a misspelled root.
