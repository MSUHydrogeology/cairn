# Plan: The usage meter counts forward and reads only new bytes

**Source proposal**: dev/proposals/archive/2026-11-16-claude-meter-reads-only-new-bytes.md
**Author**: Claude Sonnet 5.5 (`claude-sonnet-5-5`, Medium), plan author
**Status**: awaiting-plan-review
**Plan review**: required(Internal + Internal Security Review)
**Opened**: 2026-11-16
**In brief**: The usage meter will count from the day it is turned on, read only what each session log has gained, keep its private ledger to a fixed size, and say plainly when a run is incomplete.

## Build summary

After this plan the meter records where every existing session log ends the first time it runs and counts nothing before that point. Each later run reads only what a log has gained. Individual usage events are kept for at most 14 days, fewer when more than 50,000 would pile up, and older events are folded into daily totals, so the private ledger stays a fixed size. A run that stopped at its read limit reports `partial` with the reason `catching_up`, never `ok`, and the per-project summary and the pulse report say `incomplete`. `tools/session.py` is not edited.

## Source proposal

The accepted proposal (Decision 2026-11-16, standard tier) chose four changes: count forward from a start point with no back-filling (A), read each log from a saved bookmark and count only this run's bytes (B), keep individual events for 14 days and fold older ones into daily totals (C), and report an incomplete run as `partial` (D). The Maintainer also accepted a plan under `required(Internal + Internal Security Review)`. This plan carries out A to E and adds no other outcome.

**Settled design** (chunks cite the number).

- **D1 Ledger.** `LEDGER_SCHEMA` becomes `cairn-meter-ledger/5`, `READER_VERSION` `cairn-source-readers/5`. New top-level fields: `starts` (rows `{source_alias, started_at}`, one per alias, `YYYY-MM-DDTHH:MM:SSZ`), `fold_horizon` (`YYYY-MM-DD` or null), `daily` (folded rows, the `aggregates` row shape). Each cursor gains `digest` (64 hex: SHA-256 of the last complete line before `offset`, newline included; null when `offset` is 0) and `owner_key` (64 hex or null; Codex only). A ledger of schema /3 or /4 is refused and never overwritten: `Unavailable("ledger_old_schema")`. The Maintainer moves it aside to start fresh. The /3 migration goes.
- **D2 Start point.** A run reads the clock once (`_now_utc()`). An alias with no `starts` row gets one, and each of its logs gets a start bookmark from a tail read: scan back from the size at open, in 64 KiB blocks, to the last newline `L`; `offset = L + 1`; `digest` hashes the line ending at `L` (found by scanning back to the previous newline); no newline means offset 0, digest null; a line longer than `MAX_LINE` is `source_budget_exceeded` as today. Codex logs also read their first line for `owner_key` (`_digest("codex", thread)` of a valid `session_meta`, else null). Nothing before `offset` is counted. A log with no cursor under an alias that has a row is a fresh read from byte 0. On Windows the tail read arrives in C6; until then the scan treats a Windows alias as already started (a fresh read with the D7 filter).
- **D3 Modes**, per log in sorted order. Unchanged (dev, ino, size, mtime_ns, ctime_ns equal the cursor's): keep the cursor, do not open. Claude or antigravity with a cursor: resume (D4). Codex with a cursor, same dev and ino, size at least `offset`: re-read from byte 0 and count only lines that start at or after `offset`; earlier lines feed the parser and emit no event and no wait. Any failed check: fresh read.
- **D4 Resume checks.** Resume only if dev and ino match, size is at least `offset`, the byte before `offset` is `\n` (or offset is 0), and the SHA-256 of the line ending there equals `digest` (window at most `MAX_LINE + 1` bytes, counted against the run). Otherwise fresh read from byte 0 and the reason `resume_failed_<file_replaced|cursor_past_end|not_line_boundary|digest_mismatch>` in the coverage reasons. Never skip forward (the Security Review's S3 governs; the proposal's "reset to a new bookmark" would skip).
- **D5 Lines.** A read stops at the size seen at open. Only lines ending in `\n` (CRLF files end `\r\n`) are consumed; a torn tail is not counted, not in `bytes_read`, not an error. Cursor `offset` is the absolute offset after the last consumed line; `size`, `mtime_ns`, `ctime_ns` are the values at open, but `size` is `offset` when a limit stopped the read, so the next run sees a change. `line` adds the lines consumed; `generation` rises by 1 on a fresh read of a log that had a cursor. Growth during a read is left for the next run; shrink, replacement or identity change is `source_changed` as today.
- **D6 Limits.** Per piece (resumable logs): `MAX_BATCH_BYTES` (64 MiB; keep the text `MAX_BATCH_BYTES = 64 * 1024 * 1024`) and `MAX_BATCH_LINES` (100,000); a read ends at the last whole line and the run is `catching_up`. A full-size piece with no newline is a line longer than the piece: `source_budget_exceeded`, as today. Per run: `MAX_RUN_READ_BYTES` replaces `MAX_TOTAL_SOURCE_BYTES`, starting at 1 GiB (C7 fixes it); tail reads, windows, re-reads and context reads all count, and a log is not opened when nothing is left (`catching_up`). Reading also stops, with `catching_up`, once the run's events reach `MAX_RUN_EVENTS` (200,000); the old `len(incoming) > MAX_RETAINED_EVENTS` check in the scan becomes `> MAX_RUN_EVENTS + MAX_NORMALIZED_EVENTS`. A Codex re-read must fit whole: `MAX_REREAD_BYTES` 512 MiB (never above `MAX_RUN_READ_BYTES`) and `MAX_REREAD_LINES` 1,000,000 (measured largest Codex log: 321,500,887 bytes, 122,412 lines; the proposal's 64 MiB cap would block 3 of 361); over those, skipped each run with `source_too_large`; over only the remaining budget, deferred (`catching_up`).
- **D7 What counts.** Lines past a bookmark count whatever their time stamp. A fresh read counts an event only if its time is unknown, or it is not before its alias's `started_at` and its UTC day is not before `horizon_in` (`max(fold_horizon, today - 14 days)`). Waits from a fresh read are not date-filtered.
- **D8 Forks.** `read_records` already skips a fork child's copied parent events (`if copied_parent: continue`), and a fresh read drops any other old copy by D7, so a copied fork is not counted twice at any window length and the window needs no extension. A fork child is verified only against a parent batch from the same run: when a read Codex log has fork evidence and no parent batch exists, the scan reads the parent (found by `owner_key` among the prior or this run's cursors, same alias) as context only: nothing counted, cursor unchanged, bytes counted. With no such cursor the child keeps today's `fork_parent_unavailable` outcome (events counted, project unknown).
- **D9 Retention.** `FOLD_AFTER_DAYS = 14`, `RETAINED_EVENT_TARGET = 50,000` (about 761 bytes per synthetic Claude event, the ordinary review's figure, so 38 MB of the 64 MiB ledger). After merging, `horizon = max(fold_horizon, today - 14 days)`; if events with a known day on or after it, plus events with unknown time, exceed the target, raise it one day at a time, never past today. Events with a known day before it are folded into `daily` rows (project, day, tool, model, provenance, effective model), then removed with their mappings, so older days have `artifact: null` in the export. Lineages whose child events are all folded and which no retained wait cites are dropped; a proof key whose event is gone is valid. `aggregates` = retained rows plus `daily`. Project reconciliation in `_new_ledger` also applies to `daily`. The `MAX_RETAINED_EVENTS` check moves to after the fold.
- **D10 Status.** The scan adds the reason `catching_up` or `source_too_large`; `_new_ledger` then adds `incomplete`. The two refresh functions (`_refresh_ledger`, `_refresh_ledger_windows`) return `status: partial`, reason `catching_up` if present, else `source_too_large`, after writing the ledger and exports. Receipt statuses are the closed set `ok`, `partial`, `disabled`, `unavailable`; `partial` is valid only with those two reasons; any other pair is `unavailable`/`unavailable`. The receipt is `{"schema":"cairn-meter-refresh/1","status":"partial","reason":"catching_up","coverage":"unknown"}`; the text form is `meter partial: catching_up`; the exit code is 5 (today's rule, `0` only for `ok` or `disabled`).
- **D11 Print.** The export schema stays `cairn-meter-project/2`; for a partial run its sorted coverage reasons include `catching_up` (or `source_too_large`), `global_completeness_unknown` and `incomplete`. `tools/gauge.py` (the pulse report) returns `incomplete_reasons`, the sorted overlap of the reasons with those two, and prints `gauge: supplied project usage alias=<alias> aggregates=<n>; INCOMPLETE (<reasons joined by ", ">); coverage=unknown`; a complete export prints today's line. The JSON pulse carries the list. No cursor, digest, owner key or file key enters the export.
