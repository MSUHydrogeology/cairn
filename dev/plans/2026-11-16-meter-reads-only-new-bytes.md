# Plan: The usage meter counts forward and reads only new bytes

**Source proposal**: dev/proposals/archive/2026-11-16-claude-meter-reads-only-new-bytes.md
**Author**: Claude Sonnet 5.5 (`claude-sonnet-5-5`, Medium), plan author
**Status**: ready-to-implement
**Plan review**: required(Internal + Internal Security Review)
**Opened**: 2026-11-16
**In brief**: The usage meter will count from the day it is turned on, read only what each session log has gained, keep the individual events in its private ledger to a bounded number, and say plainly when a run is incomplete.

## Build summary

After this plan the meter records where every existing session log ends the first time it runs and counts nothing before that point. Each later run reads only what a log has gained. Individual usage events are kept for at most 14 days, fewer when more than 50,000 would pile up (about 3 days at today's volume), and older events are folded into daily totals, so the events in the private ledger stay bounded; waits, claims and lineages are not folded. A Codex fork child that gains a turn keeps its owner and project (today it is marked `conflicting`). A run that stopped at its read limit reports `partial` with the reason `catching_up`, never `ok`, and the per-project summary says `incomplete`; the pulse report prints INCOMPLETE for anything but a known-complete export. `tools/session.py` is not edited.

## Source proposal

The accepted proposal (Decision 2026-11-16, standard tier) chose four changes: count forward from a start point with no back-filling (A), read each log from a saved bookmark and count only this run's bytes (B), keep individual events for 14 days and fold older ones into daily totals (C), and report an incomplete run as `partial` (D). The Maintainer also accepted a plan under `required(Internal + Internal Security Review)`. This plan carries out A to E and adds no other outcome.

New top-level fields (add them to `_LEDGER_FIELDS` and to the empty ledger): `starts` (rows `{source_alias, started_at}`, one per alias, sorted by alias; `started_at` is `YYYY-MM-DDTHH:MM:SSZ` and must round-trip through `datetime.strptime` with that format), `fold_horizon` (`YYYY-MM-DD` or null), `daily` (folded rows in the `aggregates` row shape, sorted like `aggregates`). Each cursor gains `digest` (64 hex: SHA-256 of the last complete line before `offset`, newline included; null exactly when `offset` is 0) and `owner_key` (64 hex or null; Codex only). A ledger of schema /3 or /4 is refused and never overwritten: `Unavailable("ledger_old_schema")` (add the name to `_REFRESH_REASONS`); the Maintainer moves it aside to start fresh. The aggregate-row checks move into one helper used for `aggregates` and `daily`. A clock set back past a saved start makes the ledger invalid; that fail-closed result is accepted.
- **D2 Start point.** A run reads the clock once (`_now_utc()`, new: returns an aware UTC `datetime`; tests patch it) and passes it to the scan and `_new_ledger` as `now`. `_scan_approved_sources(config, prior_cursors, *, starts, now, windows_api=None, windows_user_sid=None)` takes the prior `starts` rows and returns its six values plus the new `starts` list as a seventh; `_new_ledger(..., starts=None, now=None)` takes the same two (None means the prior ledger's rows and `_now_utc()`). An alias with no row gets `{alias, now cut to whole seconds}`. A log with no cursor gets a **start bookmark** (a tail read) when its alias had no row at the start of the run, or when its alias has a row and the log's `mtime_ns` is before `started_at` (nothing after the start can be in it). Any other log with no cursor was created later and is a fresh read from byte 0 (D7). Tail read (a `tail=True` stream, D12): scan back from the size at open, in 64 KiB blocks, to the last newline `L`; `offset = L + 1`; `digest` is the SHA-256 of the line ending at `L` (scan back to the previous newline); no newline means offset 0 and digest null; more than `MAX_LINE` of torn tail or of line is `source_budget_exceeded` as today. Codex logs also get `owner_key`: the `source_owner_key` that `read_records("codex", ...)` returns over a second `piece` stream of the first line (`max_lines=1`, `budget=MAX_LINE + 1`), null when that line is not a valid `session_meta`; a Claude cursor's is null. A bookmark has `line` 0, `generation` 1, and `size`, `mtime_ns`, `ctime_ns` as at open. Tail and first-line reads count against the run limit (D6); with no budget left the log is not opened and the mtime rule bookmarks it in a later run. Nothing before `offset` is counted. On Windows the tail read arrives in C6; until then a Windows log with no cursor is a fresh read with the D7 filter in the run that adds its alias's row.
- **D3 Modes**, per log in sorted order, from the prior cursor and the enumerated `dev`, `ino`, `size`, `mtime_ns`, `ctime_ns`. (a) All five equal the cursor's: keep the cursor, do not open. (b) Claude or antigravity with a cursor: resume (D4, D12): the stream seeks to `offset`. (c) Codex with a cursor: re-read from byte 0 with the D4 checks made on the way through (D8, D12); lines up to the bookmark are parsed and not counted. (d) Any failed check: fresh read from byte 0 with `generation` + 1 and the D4 reason in the run's coverage reasons. (e) No cursor: D2. Until C2, case (b) and (c) are also a fresh read.
- **D4 Resume checks.** Four, all of which must hold: `dev` and `ino` equal the cursor's; size at open is at least `offset`; the byte before `offset` is `\n` (or `offset` is 0); the SHA-256 of the line ending at `offset` equals `digest`. They run in the order listed and the first failure gives the reason `resume_failed_<file_replaced|cursor_past_end|not_line_boundary|digest_mismatch>`; a failure never skips forward (the proposal's S3 governs; its "reset to a new bookmark" would skip). Claude and antigravity: `_resume_window_verdict` (D12) over the window of at most `MAX_LINE` + 1 bytes before `offset`, read before the seek. Codex: the same verdict from the line that ends exactly at `offset` while the stream passes it (no extra read); no line ending there is `not_line_boundary`; a different `dev`/`ino` or `size < offset` is decided before reading. Every byte read counts against the run limit.
- **D5 Lines.** A piece read stops at the size seen at open. Only lines ending in `\n` (a CRLF line ends `\r\n`) are consumed; a torn tail after the last newline is not consumed, is not an error and adds no `partial_tail`. The stream reports `end_offset` (the absolute offset after the last consumed line) and `bytes_read` (every byte physically read: window, consumed lines and torn tail; the run limit counts this). The new cursor has `offset = end_offset`, `digest` of the last consumed line, `line` plus the lines consumed (a fresh read or Codex re-read: all lines), `size`, `mtime_ns`, `ctime_ns` as at open, except `size = end_offset` when a limit stopped the read (so the next run sees a change). With no line consumed the old `offset`, `digest` and `line` stay and only `size`, `mtime_ns`, `ctime_ns` update. `generation` rises by 1 on a fresh read of a log that had a cursor. Growth during a read is left for the next run; a size below the size at open, a replaced file or an identity change is `source_changed`, as today.
- **D6 Limits** (how they interact). `MAX_LINE` (1 MiB) is unchanged and a longer line is `source_budget_exceeded`. A Claude or antigravity piece is `min(MAX_BATCH_BYTES, remaining)` bytes and at most `MAX_BATCH_LINES` lines (64 MiB and 100,000; keep the text `MAX_BATCH_BYTES = 64 * 1024 * 1024`); a piece that stops at either limit before the open size ends at the last whole line and the run is `catching_up`; a piece that consumed no line because of a limit leaves the cursor unchanged and is also `catching_up`. A Codex log is read whole or not at all: `MAX_REREAD_BYTES` (512 MiB) and `MAX_REREAD_LINES` (1,000,000; keep the texts `MAX_REREAD_BYTES = 512 * 1024 * 1024` and `MAX_REREAD_LINES = 1_000_000`, once each, for the Windows node in C6) are its limits and also the ceilings a `piece` stream accepts (D12), replacing the two `MAX_BATCH_*` ceiling checks for those streams only (measured largest Codex log: 321,500,887 bytes, 122,412 lines; the proposal's 64 MiB would block 3 of 361). A Codex log whose enumerated size exceeds `min(MAX_REREAD_BYTES, MAX_RUN_READ_BYTES)`, whose stream stops at a limit when the budget was that cap, or whose batch carries `source_budget_exceeded` (`read_records` clears its candidates above `MAX_NORMALIZED_EVENTS`) is skipped with the cursor unchanged and the reason `source_too_large`, every run; its bytes still count. A Codex log that fits those caps but not the remaining run budget is not opened: `catching_up`. Run: `MAX_RUN_READ_BYTES` replaces `MAX_TOTAL_SOURCE_BYTES`, starts at 1 GiB, is never below `MAX_REREAD_BYTES` (a test asserts it; C7 fixes it) and counts every byte read (tail, first-line, window, piece, re-read and context reads); a log is opened only while `remaining > 0`. `MAX_RUN_EVENTS` (200,000) counts the events kept from each batch; once reached the later logs are not opened (`catching_up`), and the scan's last check `len(incoming) > MAX_RETAINED_EVENTS` becomes `> MAX_RUN_EVENTS + MAX_NORMALIZED_EVENTS`.
- **D7 What counts.** Lines after a bookmark count whatever their time stamp. A fresh read counts an event only if its time is unknown, or it is not before its alias's `started_at` and its UTC day is not before `horizon_in` = `max(fold_horizon, today - FOLD_AFTER_DAYS)` (`fold_horizon` is null until C4); a fresh-read wait counts only if its `started_at_ms` is unknown or not before `started_at`. Waits are never folded or day-filtered otherwise. The filters run in the scan, after fork verification (D8), never inside `read_records`.
- **D8 Codex re-reads and forks.** `read_records` parses every line it is given, so a re-read batch holds the same events, `checkpoint_sequence`, `fork_evidence` and `wait_candidates` as a full read, and `_verify_copied_forks` is called on those whole batches and stays unchanged. Two additions to `read_records`: the candidate tuples gain a fifth item, the line ordinal (in scope at both append sites), and the batch returns `event_last_line` (event key to the latest line ordinal that produced it). Counting is decided afterwards, in the scan, once per batch: `first_counted` is `stream.checkpoint_line + 1` for a Codex re-read whose checks passed (D12) and 1 for a fresh read; the scan then drops from `batch["events"]` every event with `event_last_line < first_counted` and, on a fresh read, every event that fails the D7 filter, and skips wait candidates with `_line_ordinal < first_counted` when it builds wait rows (the set `independently_owned_waits` is built first, from all candidates). An event dropped there never reaches `_merge_event_batches`, the waits or the totals. Copied parent events are not counted twice: `read_records` already skips a child's copied parent events (`if copied_parent: continue`) and a fresh read drops older copies by D7, at any window length. **Parent context read.** When a batch to be counted has `fork_evidence` and no batch of this run passes `_verify_copied_forks`' parent test (same alias, no fork evidence, same `source_owner_key`, session and header keys), the scan reads the parent as context. After the last log of a source is processed (inside the source's `try`), for each such child, in `file_key` order, at most 4 prior cursors of the same alias with `owner_key == fork["parent_key"]` whose log exists in this run's enumeration and was not read this run are read whole from byte 0 under the Codex limits and the run budget. Each result is a batch with `context_only = True`, its `source_alias`, `file_key` and `cursor` (the prior cursor, unchanged) set; it is passed to `_verify_copied_forks` with the others and to `independently_owned_waits`, and nowhere else: its events, waits, cursor and issues never reach the merge, the wait rows, the saved cursors or the coverage reasons. If the run budget cannot cover the parent, the child's batch is dropped (no events, cursor unchanged, `catching_up`): a child is never counted unverified for lack of budget. Any other failure (no cursor with that `owner_key`, log gone, `source_too_large`) leaves today's `fork_parent_unavailable` outcome (events counted, project unknown). **Grown fork child.** Today a fork child that gains a turn is marked `conflicting` for good (reproduced). `_merge_lineage_history` instead replaces a lineage's only proof when the new proof equals it in every `_lineage_semantics` field except `child_sequence` and `child_event_keys` and the old `child_sequence` is an exact prefix of the new; any other difference keeps today's `conflicting` rule. **Loader.** A proof's `child_event_keys` may name events the ledger does not hold (uncounted before a bookmark, or folded); `_load_ledger` accepts a key whose event is absent and still refuses a present event whose `lineage_key` differs. The Security Review's alternative, removing folded keys from the proof at fold time, cannot work: `_validate_lineage_proof` requires `child_event_keys` to equal the keys of `child_sequence` (lines 2298 to 2301) and re-adds the running totals over the whole sequence (lines 2325 to 2332).
- **D9 Retention.** `FOLD_AFTER_DAYS = 14`, `RETAINED_EVENT_TARGET = 50,000` (759 to 761 bytes per synthetic Claude event, so about 38 MB of the 64 MiB ledger) and `FOLD_FORCE_EVENTS = 80,000` (about 61 MB). In `_new_ledger`, after the events are merged and every project and lineage adjustment is made (remove the `MAX_RETAINED_EVENTS` check from `_merge_events`), compute the horizon: the earliest day in `[today - 14 days, today]`, and not before the saved `fold_horizon`, such that the events with a known day on or after it plus all unknown-time events number at most the target (count events per day, then walk the days). **No horizon rise while catching up.** A run whose coverage reasons include `catching_up` folds only events already older than the saved `fold_horizon` (a late line; the loader needs that) and does not raise it, unless retained events exceed `FOLD_FORCE_EVENTS`, when it uses the full horizon. The reason: a reply whose usage lines straddle a piece boundary must still meet its first half in the retained events, or both halves would reach `daily`. Events with a known day before the horizon pass through `_recompute_aggregates` into rows, which `_add_rows` adds to `daily` rows of equal key; those events and their mappings are removed, so the export shows those days with `artifact: null`. The saved `fold_horizon` is that horizon and is never lowered. Unknown-time events never fold. A `verified` lineage whose child events are all folded or absent and which no retained event or wait cites is dropped; a `conflicting` one is kept. `aggregates` = retained rows plus `daily`, sorted by the aggregate key. `_new_ledger`'s project reconciliation also runs on `daily` rows (a removed or changed project sets `project_alias` to null; rows of equal key add). The check `len(events) > MAX_RETAINED_EVENTS` (`Unavailable("source_budget_exceeded")`) now runs after the fold. The export adds each `daily` row of its project as a row with `artifact: null`. Stated limits, not measured: a folded day keeps the project attribution it had when folded; a session-digest collision (8 hex digits) between a folded event and a retained wait is no longer seen by `_wait_artifact_map`; a reply whose second usage line is stamped more than 14 days after the first and arrives after the first was folded counts twice.

- **D12 Stream** (shared by C1, C2, C3, C6). `_ApprovedLineStream`, `_WindowsApprovedLineStream` and `_iter_approved_lines` gain the keywords `piece=False`, `max_lines=None`, `resume=None` (a dict `{dev, ino, offset, digest}`), `reread=False` and `tail=False`. With the defaults every behavior is today's, including the `MAX_BATCH_BYTES` and `MAX_BATCH_LINES` errors, `partial_tail` and `_git_helper_source`'s use of the Windows class, so the four POSIX nodes in Scope pass unedited. With `piece=True` the stream accepts `budget` up to `MAX_REREAD_BYTES` and `max_lines` (None means `MAX_BATCH_LINES`) up to `MAX_REREAD_LINES`; it stops at the size at open; a limit (`budget` bytes after the start, or `max_lines` lines) ends it at the last whole line and sets `limit_stop = True` with `terminal_reason` still None; a torn tail is ignored; growth is tolerated; shrink or identity change is `source_changed`. Outputs (all stream attributes): `end_offset`, `bytes_read`, `complete_lines`, `limit_stop`, `resume_failure` (None or one of the four D4 names), `checkpoint_line`, `tail_offset`, `tail_digest`, `open_identity`, `final_identity`, `terminal_reason`. With `tail=True` (and `piece=True`; `budget` is `2 * MAX_LINE + 2`) the stream makes the same open and end checks, yields no line, reads back from the size at open as D2 says and sets `tail_offset` and `tail_digest` (the start bookmark). With `resume` and not `reread`: after the `dev`/`ino`/size checks the stream reads the window, applies `_resume_window_verdict`, seeks to `offset` and reads on; a failed check ends it with `resume_failure` set and no lines. With `resume` and `reread` (Codex): it reads from byte 0, yields every line, and when a line ends exactly at `offset` hashes it, sets `checkpoint_line` to that line's ordinal (the number of lines through it; 0 when `offset` is 0) and compares the digest; a mismatch sets `resume_failure = "digest_mismatch"`, and no line ending at `offset` sets `not_line_boundary` at the end. The scan reads `resume_failure` after the stream ends: Claude restarts with a plain stream; Codex treats the batch just read as a fresh read (`first_counted` 1, D7 filter, `generation` + 1), so no second read is made. Shared base-class helpers used by both classes (the Windows class adopts them in C6): `_LineCutter` (cuts blocks into complete lines, enforces `MAX_LINE`, keeps the pending tail), `_resume_window_verdict(window, offset, digest)` (a pure function: the window must end in `\n`, else `not_line_boundary`; hash the bytes after the previous `\n` in the window, else `digest_mismatch`; a window with no earlier `\n` while `offset` exceeds its length is `digest_mismatch`) and `_request_error()` (checks the keyword values and ceilings and returns the reason or None). Seeking: POSIX `os.lseek(fd, offset, os.SEEK_SET)`; Windows `api.seek_to(handle, offset)`, a new method beside `seek_zero` that sets the file position the same way but raises `Unavailable("source_read_unavailable")`; `seek_zero` keeps `ledger_write_failed`, and both call one `_set_position(handle, offset, reason)`. In `piece` mode any failure to read file identity, to seek or to read ends the stream with `terminal_reason = "source_read_unavailable"`: never a resume, a skip or a fresh read.
