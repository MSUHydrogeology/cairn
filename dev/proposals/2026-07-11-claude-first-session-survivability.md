## Context

The broad-look audit's Theme 5 ("The path we've built is not the path the postdoc will walk") closes on the day-one breakers (item 10), two of which were **reproduced end-to-end**. Our first external adopter is a hydrogeology postdoc with an *existing* codebase and a conda/pyenv workflow — the exact environment these breakers fire in. Each is verified below.

**Finding 1 — skills silently unreachable, plus a phantom command in the closing line.** The lifecycle skills fan out to per-harness read-paths from a data table: `templates/skills/_data/vendor_targets.yml:12-19` puts `claude-code` on the **symlink tier** at `.claude/skills`. In `bootstrap/_scaffold/install.py:569-572`, `fan_out_skills` computes `dst = target / path` and, when `dst.parent` (i.e. `.claude/`) does not exist, appends the row as `("claude-code", "symlink", "skipped-vendor-absent")` and `continue`s — no write. The report loop in `bootstrap/_scaffold/cli.py:502-504` then **filters that status out**: `if status not in ("noop", "skipped-vendor-absent"): print(...)`. So on the likeliest first-session state — the adopter has not launched their harness yet, so `.claude/` does not exist — the skip is **silent**. Worse, `cli.py:485-487` unconditionally prints an invitation: ``Try `session-start` (/good-morning).`` The `/good-morning` slash-command **does not exist**: `grep -rn good-morning templates/ bootstrap/` finds it only as prose ("good-morning" nickname) in `templates/skills/session-start/SKILL.md:3,8`; the skill's actual `name:` is `session-start` (SKILL.md:2), and the only place `/good-morning` (with the slash) appears anywhere is `cli.py:487`. So the adopter is told nothing about the skip **and** invited to run a command that cannot work.

**Finding 2 — a stale interpreter hard-fails the daily loop.** `install.py:353,363,366-368` (`write_local_env`) records `str(Path(sys.executable).resolve())` into the untracked `dev/.cairn/local-env.json`; its own docstring (`install.py:342-345`) notes that `.resolve()` "dereferences every symlink component" — so under conda/homebrew/pyenv this bakes a **version-specific absolute path** (`.../envs/foo/bin/python3.13`). A routine env rebuild deletes that path. The reader `_resolve_interpreter` in `templates/skills/_lib/lifecycle.py` treats an **absent** config as a graceful fallback (`:349-351` → `return sys.executable, "fallback"`), but a **recorded-then-deleted** binary reaches the strict-schema check at `:387-390` (`if not interp.is_file() or not os.access(interp, os.X_OK): raise LifecycleError('… is not an executable file: {interp}.')`). The message carries **no recovery guidance**, and the call sites are **unguarded**: `cmd_session_start` calls `_resolve_interpreter` at `:698` with no local `try/except` (contrast `:653-657`, where the self-heal *is* wrapped and degraded to a warning), and `_do_full_handoff` calls it at `:1155`. The exception propagates to `main` (`:1270-1272`), which prints `ERROR:` and returns `1`. Net: after an ordinary conda rebuild, `session-start` and the goodnight handoff **refuse to start**, with a message that reads like tamper detection, not "your env moved."

**Finding 3 — onboarding seeds are copied by preset name, not by the resolved roster.** `install_onboarding` (`install.py:924-931`, signature `(templates_root, target, preset_name, *, dry_run, force)` — **no axes**) copies `templates/onboarding/{preset_name}.md` (`:1044`), extracts its seed tasks (`:1054`), and substitutes them into `dev/PLANNING.md`'s `onboarding-tasks` slot (`:1067-1082`) — keyed purely on `preset_name`. But the **module roster resolves separately**: `config.py:870-875` (`_TEAM_STAFFING_GATES`) staffs `coordination-tiers` only for `agent_team ∈ {concurrent-multi-type, concurrent-single-type}` and `dual-review` only for `{concurrent-multi-type}`; `config.py:882-887` (`_can_staff_module`) reads the **resolved** axes; and `config.py:973-988` (`resolve_axes`) lets an adopter override any single axis away from the preset's canonical point. **Reproduced:** preset `collaborative-team` (canonical `agent_team=concurrent-multi-type`, `config.py:908-920`) with an override `agent_team: single` resolves a roster that staffs **neither** coordination module, so `tools/intent.py` — which installs **only** as part of `coordination-tiers` (`config.py:513-543`) — is absent. Yet the copied seed still carries `[seed; id: install-work-intent-hooks]` instructing ``Run `python tools/intent.py …` `` (`templates/onboarding/collaborative-team.md:47-53`), plus `read-coordination-doctrine` (`:41`) and `read-dual-review-module` (`:58`). The day-one task list commands tools that were never installed. (`high-rigor-legacy.md` carries the same two coordination seeds and is exposed the same way; `solo-greenfield.md` carries none — verified: `grep -c` returns 4 / 2 / 0.) The mechanism to gate seed blocks **already exists**: `config.py:1004+` (`strip_conditional_regions`) implements `<!-- cairn:if AXIS in v1,v2 -->` region semantics and is already applied to always-on files during `install_core` (`install.py:251-252`, `:1531`); `install_onboarding` simply never calls it.

**Finding 4 (related; daily-loop truthfulness) — `session-start` self-describes as read-only but performs a self-heal write.** `templates/skills/_lib/lifecycle.py:32-33` claims "Every side-effecting subcommand honors `--dry-run`: it prints the planned writes and exits writing nothing"; the parser calls `session-start` "Read-only orientation" (`:1207`, `:1215-1216`). But `cmd_session_start` performs the **skills fan-out self-heal** (`:645-657` → `_heal_skills_fanout`, which creates symlinks, appends `.gitignore` entries, and quarantines divergent copies — `:589-623`, `:551-582`), and `session-start` has **no `--dry-run` flag** (`:1218-1231`). This is not a doctrine gap — `doctrine/session-routines.md:66-67` already says: "The only write the routine itself makes is the tool's idempotent skills self-heal, not the agent's." The *tool's own self-description* is what is inaccurate. I argue below that this belongs in scope, and offer the Maintainer an explicit split.

The fix, per finding: **surface the skip with a remedy and drop the phantom command; degrade gracefully on a moved interpreter while keeping the tamper posture; gate seeds by the resolved roster using the mechanism that already exists; correct the tool's self-description to match its own doctrine.**

## Proposal

Four fixes, one argument (the first session must survive an ordinary environment and never lie about its own state). Each is narrow and independently revertable.

### Finding 1 — honest fan-out report + real invitation (`bootstrap/_scaffold/cli.py`)

* **Surface the skip with a one-line remedy.** In the report loop (`cli.py:502-504`), stop dropping `skipped-vendor-absent`; print it as an advisory row naming the harness and the fix — e.g. *"Skills fan-out [symlink] claude-code: skipped (your harness's config dir does not exist yet) — it is created the first time you launch the harness; re-run bootstrap, or `python tools/lifecycle.py session-start`, self-heals the link once the dir exists."* This is accurate: the `session-start` self-heal fans out precisely when `dst.parent.exists()` (`lifecycle.py:614`). Keep the phrasing vendor-neutral (the harness name comes from the data row, as it already does for copy/symlink rows).
* **Drop the phantom command.** Correct `cli.py:487` so it names only the real invocation. The skill's `name:` is `session-start` (its slash form, where a harness surfaces it, is `/session-start`); the always-works form is `python tools/lifecycle.py session-start`. The `(/good-morning)` parenthetical is removed (it is a spoken nickname, not a command). The plan pins the exact wording; the invariant is *the report names no command that is not installable*.

### Finding 2 — graceful degrade on a moved interpreter, tamper posture preserved (`templates/skills/_lib/lifecycle.py`)

The security-sensitive core. The `local-env.json` schema is a deliberately strict, tamper-aware trust root — a *redirect* to a different executable must stay fatal. The refinement distinguishes **"the recorded path is simply gone"** (an env rebuild) from **every other strict-schema violation** (the tamper shapes):

* In `_resolve_interpreter`, when the recorded interpreter path **does not exist at all** (the leaf is absent — not a present-but-non-executable file, not a symlinked leaf/parent, which are already rejected earlier at `:382`), **degrade to the runtime-resolver fallback** (`sys.executable`) with a loud, named warning and remedy — the same fallback the absent-config branch already uses (`:349-351`), plus a one-liner ("recorded interpreter `<path>` no longer exists — your environment was likely rebuilt; using the current interpreter. Delete `dev/.cairn/local-env.json` or re-run bootstrap to refresh the binding"). Return source `"fallback-stale"` so `cmd_session_start`'s interpreter section (`:702-710`) reports it.
* **Everything else stays fatal.** A present path that is not an executable file, any symlinked component, a relative path, control characters, extra keys, or unreadable JSON continue to `raise LifecycleError` — these are the tamper/malformation shapes, unchanged.
* **Why this is safe.** A tamper attack redirects the binding to a *different existing* executable, which still passes `is_file()`/`X_OK` and never enters the new absent-path branch — so it is not degraded. A deleted binary only forces a fallback to the interpreter already running the CLI, which is the exact safety the absent-config case already accepts ("safe because the lifecycle tools are standard-library only", `:345-347`). This is a **synthesis of two existing doctrines**, not a new rule: the "degraded assurance / named forfeiture" posture (`doctrine/runtime-contract.md:139`) and "fail-open … degrades gracefully" (`doctrine/session-routines.md:416`), reconciled with the trust-root's fail-closed-on-tamper stance.
* No change to `write_local_env` (`install.py`): resolve-don't-bake stays; the reader simply stops treating "my env moved" as an attack.

### Finding 3 — gate onboarding seeds by the resolved roster (`bootstrap/_scaffold/install.py` + preset files)

Reuse the existing conditional-region mechanism rather than inventing a new one (this is the trap `automated-review-committer` fell into — inventing a mechanism doctrine already had):

* **Thread the resolved axes into `install_onboarding`.** Add an `axes: dict | None` parameter and pass `resolved_axes` from the one call site (`cli.py:522-525`, where `resolved_axes` is already in scope at `cli.py:465`). Apply `strip_conditional_regions(preset_text, axes)` (`config.py:1004+`) to the preset text **before** `_extract_seed_tasks`, exactly as `install_core` already does for always-on files (`install.py:251-252`).
* **Mark the roster-dependent seed blocks** in `templates/onboarding/collaborative-team.md` and `templates/onboarding/high-rigor-legacy.md`: wrap `install-work-intent-hooks` and `read-coordination-doctrine` in `<!-- cairn:if agent_team in concurrent-multi-type,concurrent-single-type -->` (they need `coordination-tiers`), and `read-dual-review-module` in `<!-- cairn:if agent_team in concurrent-multi-type -->` (it needs `dual-review`) — mirroring `_TEAM_STAFFING_GATES` (`config.py:870-875`) exactly. `strip_conditional_regions`' keep-on-missing-axis default (`config.py:1020-1024`) means the change is a no-op for any path that does not resolve `agent_team`, so nothing else moves.
* **Drift guard** (`bootstrap/tests/test_onboarding_seed_roster.py`): for each preset × each axis override that unstaffs a module, assert the *rendered* `PLANNING.md` seed contains no reference to that module's installed tools (e.g. no `tools/intent.py` when `coordination-tiers` is unstaffed) — a fail-closed test keyed to the roster, so the condition-vs-gate correspondence cannot silently drift.

### Finding 4 — correct the self-description (`templates/skills/_lib/lifecycle.py`)

* Reword the module docstring (`:32-33`) and the parser text (`:1207`, `:1215-1216`) so `session-start` is described as **"orientation gather plus one idempotent skills-fan-out self-heal write"**, not "read-only"; scope the "every side-effecting subcommand honors `--dry-run`" claim to the subcommands that actually do (`session-end`), matching `doctrine/session-routines.md:66-67`. **Pure text accuracy — no behavior change, no new flag.** (Adding a `--dry-run` to `session-start` is a feature, a different risk class; explicitly *deferred*, see Alternatives.)

**Scope argument for Finding 4.** It belongs here: (a) same theme — truthfulness of shipped, adopter-facing self-description in the first-session/daily loop; (b) it aligns shipped text with *existing* doctrine (no doctrine change, zero behavior change — the lowest-risk of the four); (c) it edits the *same file* as Finding 2 (`lifecycle.py`), so bundling avoids two separate reviews of one shipped tool. It is the **weakest-fitting** of the four (a daily-loop item, not strictly a day-one breaker); the Maintainer may split it (Alternative 4) at no cost to the others.

## Rationale

* **Which user workflow does it improve?** The postdoc's very first session and daily loop. Today, on the most likely first-session state their skills are silently unreachable and they are pointed at a command that does not exist (Finding 1); after their first conda rebuild the daily routine refuses to run (Finding 2); and a customized install hands them a task list commanding absent tools (Finding 3). Each is a concrete, reproduced dead-end at the exact moment first impressions form.
* **What contract/boundary does it preserve or clarify?** The install report and the shipped tool's self-description become **truthful** about what happened and what the tool does — the honesty property Cairn sells. The `local-env.json` **trust-root contract** is *preserved* (tamper stays fatal) while a legitimate env move stops masquerading as an attack. The roster→seed correspondence is made a **checked invariant** instead of an assumption.
* **Correctness/reproducibility improved?** The seed list now reflects what was actually installed; the daily loop survives the environment churn that is normal lab life; a skeptic re-running the install sees an accurate report.
* **Why now?** These are Phase A ("before the postdoc installs"). The install is imminent and one-shot; two of these are reproduced end-to-end. There is no cheaper time to fix a first-session breaker than before the first session.

## Alternatives considered

1. **Do nothing.** Rejected — the day-one breakers ship into the one-shot first adoption; two are reproduced; the closing install line actively misdirects.
2. **Fix only the two reproduced breakers (Findings 1 + 2), defer 3 + 4.** Partial — Finding 3 is also reproduced (preset + single override) and hits the postdoc's likely first customization; Finding 4 is near-free and shares a file with Finding 2. Deferring them leaves a customized install lying about its task list.
3. **Split Finding 2 into its own Security-Reviewed proposal.** Viable and *offered to the Maintainer*. Argument for keeping it here: it is a ~10-line, conservatively-scoped refinement to one function that preserves the tamper posture, and holding it back leaves the reproduced conda-rebuild breaker unfixed for the imminent install. Argument for splitting: it is the only finding touching a security trust root, and a different risk class deserves its own record. I default to **keep, with an explicit Security-Review recommendation** (Plan-review line), and defer the split to the Maintainer.
4. **Split Finding 4 out.** Viable at no cost to the others (it is text-only and self-contained). I default to keeping it (same file as Finding 2, same theme) but flag it as the natural drop point if the panel wants a tighter scope.
5. **Finding 2, naive form: make *every* strict-schema violation degrade to fallback.** Rejected — that would weaken the tamper-aware trust root (a redirected/symlinked/non-executable binding would silently run something else). Only pure *absence* degrades.
6. **Finding 3, invent a per-seed module-dependency annotation + a new filter.** Rejected — `strip_conditional_regions` / `cairn:if` already gates content by resolved axis and is already wired through the installer; a new mechanism would duplicate it (the "don't invent a mechanism doctrine/engine already has" lesson).
7. **Recommended: all four, Finding 2 designed conservatively, with External + Security-Review before the Decision.**

## Signals the change is wrong

* **Finding 1's advisory row becomes noise** — if most real installs *do* have `.claude/` and the row prints spuriously, it trains adopters to ignore the report. Recovery: only print the row when a symlink-tier target is genuinely absent (already the trigger), or downgrade to a single summarized line.
* **Finding 2's degrade masks a real problem** — if an adopter's binding is silently wrong in a way that isn't pure absence and we widened the branch too far, a broken interpreter runs anyway. Recovery: the carve is deliberately narrow (absent leaf only); if review finds the boundary fuzzy, keep it fatal and add only the recovery guidance to the message (a strictly smaller change).
* **Finding 3's `cairn:if` condition drifts from `_TEAM_STAFFING_GATES`** — if a future gate change isn't mirrored in the preset markers, seeds mis-fire again. Recovery: the drift-guard test is keyed to the *resolved roster* (not the marker), so it fails closed when the two diverge; if that proves insufficient, generate the markers from the gate table.
* **Finding 4 over-corrects** — if "not read-only" reads as "session-start is destructive," it could scare adopters off the routine. Recovery: keep the framing to "orientation plus one idempotent self-heal," which is exactly what doctrine already says.
* **Bundling was wrong** — if review judges Finding 2's security surface or Finding 4's looser fit warrants isolation, split per Alternatives 3/4; the other findings stand alone and land unchanged.
